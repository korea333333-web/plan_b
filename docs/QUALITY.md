# 품질 기준 — 현재 MVP

## 1. 기본 게이트

```bash
pnpm run lint
pnpm run build
pnpm test
pnpm exec next build
```

`pnpm test`와 `pnpm run build`는 vinext·Sites 경로를 확인한다. `pnpm exec next build`는 Vercel용 Next.js 빌드 경로를 확인한다. 두 빌드 모두 Supabase 브라우저 클라이언트가 서버 렌더링 단계에서 `window`에 접근해 실패하지 않는지 함께 확인한다.

## 2. 현재 자동 테스트 범위

`tests/planner-engine.test.mjs`:

- 윤년을 포함한 날짜 더하기
- 월요일 시작 주간 날짜
- 날짜 범위 검증
- 자동 계획의 선택 요일·시간·하루 한도
- 겹치는 가능 시간 병합
- 부족한 분량 반환
- 종료 전 planned와 종료 후 unconfirmed 계산
- 반복 계획의 완료 상태가 선택한 발생 날짜에만 적용되는지
- 판정된 발생 회차만 사용하는 전체 완료율
- 일정이 있는 날 기준 연속 달성
- 화산오검 순환과 확정 대사

`tests/supabase-plans.test.ts`:

- Supabase snake_case 행을 화면 계획으로 변환
- 반복 요일과 발생 날짜별 상태 JSON 정리
- 신규 계획 INSERT payload와 부분 UPDATE payload
- 잘못된 ID와 행 값 방어
- 레거시 계획과 Supabase 계획의 중복 서명
- 중복 서명이 저장소별 ID, 사용자 ID, 시각과 판정 상태에 의존하지 않는지

`tests/rendered-html.test.mjs`:

- production worker가 200 HTML을 반환
- 제목과 인증 확인 또는 `Google로 계속하기` 진입 화면
- 로그인 뒤 사용하는 세 탭 라벨이 제품 코드에 존재
- 친구 메뉴 부재
- 빈 상태 문구
- 시안용 예시 일정 부재
- 핵심 확정 대사가 엔진에 존재
- 빈 상태 장식이 모바일 CTA의 포인터 입력을 막지 않는 CSS 회귀
- 탭 전환 시 맨 위로 이동하는 공통 내비게이션 사용
- 기록 탭의 사용법 안내와 판정 전 빈 상태 문구
- 자동 생성 3단계 안내와 미리보기 버튼 문구
- 원형 그래프의 24개 시간 숫자 렌더링
- 완료 1회당 매화 1송이 규칙과 기존 10단계 비율 계산의 부재

현재 자동 테스트에 없는 것:

- 실제 Google OAuth 리디렉션·로그인 통합 테스트
- 실제 Postgres CRUD와 RLS 정책 통합 테스트
- 서로 다른 계정·기기의 교차 동기화 E2E
- 기존 Vercel `localStorage`와 Sites D1을 함께 사용하는 가져오기 E2E
- 가져오기 또는 자동 생성 저장의 롤백 테스트
- 브라우저 상호작용과 시각 회귀
- 월간 통계 테스트

없는 자동 검증을 통과 조건처럼 문서화하지 않는다.

## 3. 테스트 준비

수동 검증 전 다음을 준비한다.

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
- Google OAuth가 활성화된 Supabase 프로젝트와 올바른 콜백·반환 주소
- Google 테스트 계정 A
- 계정 A와 다른 Google 테스트 계정 B
- RLS가 활성화되고 사용자별 SELECT, INSERT, UPDATE, DELETE 정책이 적용된 `public.plans`

브라우저 환경 변수에는 Supabase URL과 publishable key만 사용한다. OAuth 공급자 비밀값이나 service role key를 저장소 또는 브라우저 환경 변수에 넣어 테스트하지 않는다. 그렇게 하면 실제 로그인·RLS 경로를 검증할 수 없다.

## 4. 필수 수동 스모크 테스트

### 인증

1. 로그아웃 상태에서 계획 내용 대신 `Google로 계속하기` 버튼이 보이는지 확인한다.
2. 버튼을 누르면 Google의 계정 선택·동의 화면으로 이동하는지 확인한다.
3. 계정 A로 인증하면 허용된 원래 사이트 주소로 돌아오는지 확인한다.
4. 돌아온 뒤 세 탭과 계정 A의 빈 상태 또는 기존 계획이 보이는지 확인한다.
5. 새로고침 뒤 로그인 세션과 계정 A의 계획이 유지되는지 확인한다.
6. Google 인증을 취소하거나 OAuth 오류를 만들었을 때 한국어 오류와 다시 시도할 동작이 보이는지 확인한다.
7. 로그아웃하면 현재 브라우저의 계획 내용이 사라지고 Google 로그인 화면으로 돌아가며, 다른 기기의 세션은 유지되는지 확인한다.
8. 모바일 헤더와 PC 사이드바에서 Google 계정과 로그아웃 동작에 접근할 수 있는지 확인한다.

### Supabase 저장과 교차 기기 동기화

1. 계정 A로 직접 계획 한 건을 저장한다.
2. 새로고침 뒤 같은 계획이 다시 로드되는지 확인한다.
3. 다른 브라우저 또는 기기에서 계정 A로 로그인해 같은 계획이 보이는지 확인한다.
4. 두 번째 환경에서 완료·미완료 판정 또는 삭제를 수행하고 첫 번째 환경을 새로고침해 반영되는지 확인한다.
5. 계정 B로 로그인했을 때 계정 A의 계획이 보이지 않는지 확인한다.
6. 계정 B에서 계정 A의 행 ID로 직접 조회·변경·삭제를 시도해 RLS가 거부하는지 확인한다.
7. 로컬, Sites, Vercel에서 같은 계정 A의 계획 집합을 불러오는지 확인한다.

### 저장 오류와 재시도

1. 계획 폼에 내용을 입력한 뒤 네트워크 또는 Supabase 요청을 실패시킨다.
2. 저장 성공 화면으로 넘어가지 않고 오류와 재시도 안내가 보이는지 확인한다.
3. 실패한 새 계획이 `maewha-plans:*` 또는 D1에 자동 생성되지 않았는지 확인한다.
4. 네트워크를 복구하고 재시도해 Supabase에 한 건만 저장되는지 확인한다.
5. 조회 실패 때 빈 계획 계정으로 확정하지 않고 오류와 다시 불러오기 동작을 제공하는지 확인한다.
6. 완료·미완료 판정과 삭제 실패 때 기존 화면 상태가 성공한 것처럼 바뀌지 않는지 확인한다.
7. 1,000개를 넘는 계획도 마지막 페이지까지 불러오는지 확인한다.

### 기존 계획 가져오기

1. 현재 테스트 origin에 이전 Vercel 형식의 `maewha-client-id`와 `maewha-plans:${clientId}` 계획을 준비한다.
2. 가능하면 같은 `clientId`의 과거 Sites D1 계획도 준비한다.
3. 로그인만 했을 때 기존 계획이 자동으로 Supabase 목록에 합쳐지지 않는지 확인한다.
4. `기존 계획 가져오기`를 누르고 대상과 원본 유지 안내를 확인한다.
5. 가져온 각 계획이 계정 A의 Supabase 행으로 순차 생성되는지 확인한다.
6. localStorage와 D1에 같은 내용의 계획이 있거나 Supabase에 이미 같은 계획이 있을 때 중복 생성되지 않는지 확인한다.
7. 중간 요청을 실패시켜 일부 성공 안내와 재시도가 가능한지 확인한다.
8. 재시도 뒤 이미 가져온 같은 계획이 다시 생성되지 않는지 확인한다.
9. 완료 뒤 원래 localStorage와 D1 행이 삭제되지 않았는지 확인한다.
10. 계정 B에서는 계정 A의 가져오기 결과가 보이지 않는지 확인한다.
11. D1 후보가 500개를 넘을 때 다음 커서까지 읽고 완료 뒤에만 가져오기 완료 표시를 남기는지 확인한다.

다른 origin이나 브라우저 프로필의 localStorage는 현재 페이지에서 읽을 수 없으므로 같은 데이터가 자동 발견될 것이라고 기대하지 않는다.

### 보기 전환

1. 이전·다음 주가 이동하는지 확인한다.
2. 30분/1시간 변경 시 일정 시간이 바뀌지 않는지 확인한다.
3. 오늘의 표/원 보기가 같은 일정 집합을 표시하는지 확인한다.
4. 오늘의 원형 보기 둘레에 00시부터 23시까지 숫자가 모두 보이는지 확인한다.
5. 일정 카드를 눌러 상세 시트를 열고 삭제해 본다.
6. 320×568과 390×844에서 빈 상태의 `계획 만들기` 버튼을 실제 포인터로 눌러 작성 화면 제목과 하단 활성 메뉴가 바뀌는지 확인한다.
7. 긴 화면에서 다른 탭으로 이동했을 때 새 화면의 맨 위가 보이는지 확인한다.

### 직접·자동 작성

1. 끝 시간이 시작 시간보다 빠른 직접 계획을 거부하는지 확인한다.
2. 반복 요일 계획이 기준일 이후 해당 요일에 나타나는지 확인한다.
3. 자동 생성에서 할 일, 기간, 요일, 가능 시간, 하루 한도를 입력한다.
4. 미리보기와 부족 분량 경고를 확인한다.
5. 입력값을 바꾸면 이전 미리보기가 비워지는지 확인한다.
6. 미리보기와 저장 버튼의 역할이 3단계 안내와 일치하는지 확인한다.
7. 저장 후 생성된 전체 항목이 Supabase 계획표에 나타나는지 확인한다.
8. 자동 저장 중 요청을 실패시켜 앞선 항목만 남을 수 있고 나머지는 로컬에 폴백하지 않는지 확인한다.
9. 오류 뒤 미리보기에서 이미 성공한 항목이 빠지고, 재시도 시 남은 항목만 저장되는지 확인한다.

### 판정과 기록

1. 종료 전 일정은 `예정`이고 판정 버튼이 없는지 확인한다.
2. 종료된 미판정 일정에 `미확인`과 `뭐야, 왜 안 왔어?`가 보이는지 확인한다.
3. 반복 계획 한 회차를 판정한 뒤 다른 날짜의 같은 반복 계획 상태가 바뀌지 않는지 확인한다.
4. 완료·미완료 판정 후 순서에 맞는 토스트 대사를 확인한다.
5. 새로고침 후 반응 순번이 청명부터 다시 시작하는지 확인한다.
6. 전체 완료율이 판정된 발생 회차의 완료/(완료+미완료)인지 확인한다.
7. 연속 달성과 미확인 개수가 최대 최근 365일의 발생 회차를 기준으로 계산되는지 확인한다.
8. 기록 탭에 전체 완료율, 연속 달성, 미확인, 미완료, 최근 6개가 보이는지 확인한다.
9. 반복 일정 상세의 삭제 문구가 `반복 계획 전체 삭제`이고 삭제 시 모든 회차가 사라지는지 확인한다.
10. 계획은 있지만 아직 판정 기록이 없으면 0% 카드 대신 기록을 남기는 방법이 보이는지 확인한다.
11. 판정 기록이 있으면 한눈에 보기 다음에 최근 계획 결과, 마지막에 이번 주 매화가 보이는지 확인한다.
12. 이번 주 완료 회차를 1개, 2개로 늘릴 때 매화가 각각 1송이, 2송이만 보이며 미완료 회차는 꽃 수를 늘리지 않는지 확인한다.

## 5. 반응형 점검

점검 화면:

- 320×568
- 390×844
- 768×1024
- 1440×900

확인:

- 로그인 카드가 모든 화면에서 잘리지 않고 `Google로 계속하기` 버튼까지 스크롤 가능하다.
- 920px 이하에서 모바일 헤더와 하단 내비게이션이 나온다.
- 920px 초과에서 좌측 사이드바가 나온다.
- 계정 이메일과 로그아웃 버튼이 내비게이션을 밀어내지 않는다.
- 하단 내비게이션이 저장 버튼과 본문을 가리지 않는다.
- 저장·가져오기 배너의 버튼과 문구가 작은 화면에서도 겹치지 않는다.
- 주간표 가로 스크롤은 `.weekly-scroll` 안에서만 발생한다.
- 620px 이하에서 원형 그래프, 폼, 기록이 세로로 정리된다.
- 긴 제목과 메모가 카드 바깥으로 넘치지 않는다.
- 상세 시트와 반응 토스트가 하단 내비게이션 위에 보인다.

## 6. 접근성·모션 최소 확인

현재 MVP에서 반드시 유지할 항목:

- `Google로 계속하기` 버튼의 명확한 접근 가능한 이름
- OAuth 이동 중 버튼의 중복 실행 방지와 상태 안내
- 인증·저장 오류의 `role="alert"` 또는 상태 알림
- 입력과 버튼의 `focus-visible` 윤곽
- 아이콘 또는 X 단독 버튼의 한글 `aria-label`
- 원형 그래프 옆의 텍스트 범례
- 상태의 색상 + 한글 라벨
- 장식 꽃잎의 `aria-hidden`과 `pointer-events: none`
- `prefers-reduced-motion`에서 꽃잎 숨김

포커스 트랩, Escape로 상세 시트 닫기, 완전한 스크린리더 대화상자 의미는 현재 구현되지 않았다. 이를 구현하기 전까지 준수했다고 주장하지 않는다.

## 7. 콘텐츠 회귀 점검

배포 전에 검색한다.

- 친구, 동문, Roster, Invite가 제품 UI에 없는가
- 검술 수련, 명상, 서예 같은 Stitch fixture가 없는가
- Googleusercontent 등 Stitch 원격 이미지 URL이 없는가
- 확정 대사가 `lib/planner.ts`와 일치하는가
- 저장 실패를 “이 브라우저에 저장 중”으로 표현하는 과거 문구가 없는가
- Vercel 계획을 localStorage 전용이라고 설명하는 과거 문구가 없는가
- 핵심 인증·오류·가져오기 문구가 한국어인가

## 8. 현재 알려진 제한

- 네트워크가 없으면 새 계획을 작성·판정·삭제할 수 없으며, 나중에 자동 동기화되는 오프라인 모드도 없다.
- Google 또는 Supabase OAuth 서비스가 중단되면 새 로그인을 완료할 수 없다.
- 이메일·비밀번호 로그인과 Google 이외의 로그인 공급자는 제공하지 않는다.
- 프로필 편집과 계정 삭제 UI가 없다.
- 기존 계획 가져오기는 현재 origin과 브라우저에서 읽을 수 있는 데이터만 대상으로 한다.
- 과거 D1의 `clientId`는 인증이 아니며 레거시 조회에만 사용한다.
- 기존 계획과 Supabase 계획의 판정 상태는 자동 병합되지 않고 원본도 자동 삭제되지 않는다.
- 자동 생성과 기존 계획 가져오기는 순차 저장이라 부분 성공할 수 있다.
- 반복 계획을 삭제하면 선택한 회차만이 아니라 전체 반복 계획이 삭제된다.
- 판정 정정과 일정 내용 편집 UI가 없다.
- 보기 설정과 반응 순번은 저장되지 않는다.
- 기록은 발생 회차 집계이며 사용자 지정 주간·월간 기간 통계는 아니다.
- 실제 Google OAuth, Supabase RLS, 교차 기기와 레거시 가져오기 흐름은 아직 자동 통합 테스트가 없다.
